# 19 · 崩坏状态机：22 个状态怎么不写成一团乱麻

> 规格要求右侧窗口按歌词逐句演出 **22 个崩坏状态**（S0 整齐网格 → S21 窗口关闭）。
> 每个状态都有自己的参数、过渡时长和缓动曲线。
> 这笔记说的是**怎么组织它**，而不是每个状态画什么。

---

## 一、第一原则：把「参数」和「逻辑」分开

22 个状态如果参数写死在组件里，调一个数字要翻代码、改完要重新找。

所以分成两层：

| 层 | 放什么 | 在哪 |
|---|---|---|
| **数据层** | 触发时间、延迟、过渡时长、缓动、颜色、尺寸、频率 | `input/viz-states.json` |
| **逻辑层** | 「我这个状态长什么样」 | `src/modelviz/states/S*.tsx` |

> [!tip] 判断标准
> **如果改这个值不需要看懂代码，它就该在 JSON 里。**
> 反过来，「这个数字怎么参与画格子」是逻辑，留在代码里。

---

## 二、一个解析器回答四个问题

整台状态机只需要一个函数。给它时间 `t`，它回答：

```ts
resolveAt(t) → {
  current,        // 现在是哪个状态
  prev,           // 从哪个状态过渡过来的
  local,          // 本状态已经放映了多久
  progress,       // 过渡进度（0~1，**已经过缓动**）
  prevFade,       // 上一状态的退出进度
}
```

状态组件拿到的就是这个：

```tsx
<Comp t={t} local={local} progress={progress} params={params} ... />
```

> [!important] 关键设计：状态组件**不知道**过渡的存在
> 它只管「我这个状态完整长什么样」。
> 进出怎么做，全由外层按 `progress` 处理。
> 这样新增一个状态不需要碰任何别的文件 —— 只写一个新的 `S*.tsx`，去注册表登记一行。

---

## 三、缓动不是装饰，是规格的一部分

规格给每个过渡都指定了曲线，而且它们**不可互换**：

| 名字 | 数学 | 用在哪 |
|---|---|---|
| `easeInOut` | `x²(3−2x)` | S0→S1 错误日志「慢慢开始不对劲」 |
| `easeOut` | `1−(1−x)²` | S1→S2「立刻炸开然后稳住」 |
| `easeIn` | `x²` | S19 收拢「越来越快地被吸进去」 |
| `fastSlow` | `1−(1−x)³` | S2→S3「先一把铺满，再慢慢压上文字」 |

> [!warning] `fastSlow` 不是标准 CSS 名字
> 「先快后慢」在 CSS 里没有直接对应（`ease-out` 是减速但起点不够猛）。
> 这里单独实现：起步就冲出大半，尾巴拖长。

---

## 四、交叉过渡：为什么 S0→S1→S2 能连成一口气

S0（整齐）→ S1（错位）→ S2（碎裂）在叙事上是**同一个网格逐步坏掉**。

如果每个状态各画一套网格，交叉过渡时就是两张不同的图叠在一起 —— 崩坏感断了。

**解法**：网格只写一次（`GridField.tsx`），各状态通过**参数扭曲它**：

```
jitterPx    每格随机错位     ← S1 的 ±3px
hueShift    色相整体偏移     ← S1 的 +20
chunkBreak  切成 N 块各自位移 ← S2 的碎裂
redRatio    往红色 #FF3B30 混 ← S2 的红色归因
desat       去饱和           ← S8
```

因为几何完全一致，S0 和 S1 的网格在交叠时**每个格子都在同一个位置**，
混出来的效果就是「同一个网格开始抖动」，而不是重影。

> [!tip] 可复用的判断
> **要交叉过渡的两个画面，如果它们的「骨架」相同，过渡就会连戏；
> 骨架不同（比如聊天窗口 vs 终端），就只能硬切或过黑场。**

## 五、权重：标签不是显隐开关

规格 §2.3 给每个段落标了 `player / chat / dash / term`。
**它不是「这一刻播哪个镜头」，而是「这一刻谁在主导」。**

用户对这条的裁决很明确：

> 布局全片恒定（左聊天 + 右可视化始终存在）。
> 标签只描述权重与语气。
> **S21 之前任何一侧 opacity 都不得为 0。**

所以标签落成**四个可测参数**，一起变：

| 参数 | 低权重侧 | 高权重侧 |
|---|---|---|
| opacity | 0.35 ~ 0.42 | 1.0 |
| 饱和度 | 去饱和 | 保持 |
| 动画频率 | 变慢 | 加速 |
| 消息密度 | 变少（不是没有） | 密 |

> [!note] 一个连带发现
> 这个裁决逼出了一个小妥协：S3 是「全屏红色，只剩一行大字」，
> 但铁律说两侧不能为 0。
> 解法是红色用 `rgba(26,0,0,0.94)` —— 全屏感保留了，底下两个窗口还透出约 6%。
> **规格的两条要求冲突时，找一个同时满足两者的实现，而不是挑一条违反。**

## 六、踩到的坑：时间戳起算点搞错了

S1 的错误日志要滚动显示时间戳。我写的是：

```ts
const total = Math.floor(t * perSec);          // ✗ 从全片 0 秒起算
// 时间戳 = idx / perSec + 46.62
```

结果 `t = 48.5s`（S1 刚开始两秒）时，日志时间戳已经跑到 **95 秒**。

**原因**：`t` 是全局时间，但「已经产生了几行日志」应该从**这个状态开始的那一刻**算：

```ts
const sinceS1 = Math.max(0, t - 46.62);
const total = Math.floor(sinceS1 * perSec);    // ✓
```

> [!important] 教训
> **状态内部的计数器，起点必须是「这个状态的开始」，不是「影片的开始」。**
> 这类 bug 不会报错、不会崩，只是数字悄悄离谱 —— 只能靠看一眼截图发现。
> 所以**每个状态都要渲染静帧检查**，不能只看「渲染成功」。

## 七、时间只保存一份

触发时间本来同时写在 `viz-states.json` 和 `lyric-timing.json` 里。

**两份数据一定会漂移** —— 改了一处忘了另一处，而且不会报错。

解法：解析器以 `lyric-timing.json` 为**唯一权威**，
`viz-states.json` 里的 `at` 只是记录，加载时会被覆盖。

同理，S5 / S8 / S15 这些「同一状态里有第二个触发点」的，
用 `SUB_MARKERS` 把子触发时间也从 `lyric-timing.json` 注入到 `params`。

> [!tip] 通用原则
> **同一个事实存两遍，早晚会不一致。**
> 要么只存一份，要么在加载时强制一方覆盖另一方，并让它可检验。

---

## 八、未实现的状态要「看得出来」

S4~S21 还没做。如果不处理，它们会渲染成空白 —— 验收时容易被误判成「画面出 bug」。

所以未注册的状态自动落到一个占位组件，画面上明写：

```
NOT IMPLEMENTED
S5 · 怪物劣等感
```

> **「做到哪了」应该能在画面上看出来，而不是去查代码。**

---

## 九、验收工具：调试 HUD

`MainFilmDebug` 这个 Composition 在左下角常驻一行：

```
t=62.50 · 段4 dash · L1.00 R1.00 · S2 红色归因 · 过渡 98%
```

一眼能核对：时间对不对、段落标签是什么、两侧权重多少、当前是哪个状态、过渡走到哪了。

> 正片 `MainFilm` 不带 HUD，两个 Composition 共用同一个组件，靠传入的 `showHud` 区分。
