# 12 自动节拍检测 — 以及一个必知的坑

`tools/auto-beats.mjs` 能从一首歌直接生成打点表初稿。实测在这段测试音轨上：
**48/48 拍全部落在 10 毫秒内，中位偏差 2.2 毫秒** —— 比 24fps 的一帧（41.7 毫秒）精确一个数量级。

## 什么时候用

| 情况 | 建议 |
|---|---|
| 拿到新歌，想先看结构 | **直接跑自动检测**，几秒钟出初稿 |
| 想做精细卡点 | 自动初稿 + [[03 打点表 - 全片的地基]] 的人工打点互相校验 |
| 纯器乐 / 电子 | 自动检测通常够用 |
| 自由节奏、散板、大量变速 | 自动检测会失效，只能人工 |

自动检测的价值不只是省事，更是**交叉校验**：如果它和你的手打差很多，说明其中一方有问题。

## 流程（五步）

1. **解码**：用 Remotion 自带的 ffmpeg 转成 22050 Hz 单声道 PCM（不依赖系统 ffmpeg，见 [[09 本机环境与技术决策]]）
2. **分帧**：`FRAME = 1024` 采样一窗，`HOP = 256` 步进 → 每秒约 86 个分析帧
3. **分频段算能量**：低频（底鼓）/ 中频 / 高频（军鼓、踩镲），取「能量的正向增量」当起音强度
4. **自相关**：对起音强度序列做自相关 → 主周期 → BPM
5. **定相位 + 细化**：穷举相位找起音最强的位置；再把每个拍点**吸附到附近起音峰**，用加权最小二乘拟合 `t_k = phase + k·period`

## ⚠️ 核心坑：分帧带来的时间偏置

> [!warning] 这个坑会让**全片**卡点系统性偏移，而且不会报错
> 直接「把帧号当时间」写作 `t = i / ENV_RATE`，会让所有拍点**偏早 34.8 毫秒**（约 0.8 帧 @24fps）。

**推导**：第 `i` 帧的能量来自样本区间 `[i·HOP, i·HOP + FRAME)`。
一个瞬态落在样本 `T` 时，它第一次进入窗口的条件是 `i·HOP + FRAME > T`，即

```
i_first = floor((T − FRAME) / HOP) + 1
```

反解出 `T`：

```
T ≈ i_first · HOP + FRAME − HOP
```

所以正确的换算必须把 `FRAME − HOP` 这段补回来：

```js
const OFFSET_SEC = (FRAME - HOP) / SR;              // (1024−256)/22050 = 0.0348 秒
const toSec = (frame) => frame / ENV_RATE + OFFSET_SEC;
const toFrame = (sec) => (sec - OFFSET_SEC) * ENV_RATE;
```

**注意**：如果只用「窗口中点」`FRAME/2` 来修正，只补回一半，还会剩约 12 毫秒偏差。

### 实测对照

| 阶段 | 中位偏差 | 系统偏移 | 最大偏差 |
|---|---|---|---|
| 修正前 | 37.1 ms | −37.0 ms | 495.7 ms |
| 修正后 | **2.2 ms** | −2.2 ms | **4.3 ms** |

修正前那 37 毫秒是**纯系统性偏差**——所有拍点一起早，听感上就是"画面老是抢拍"。

## 第二个坑：开头第一拍检测不到

起音「进入窗口」的那次能量跳变正好落在第 0 帧，而 `novelty[0]` 按定义是 0（没有前一帧可比），
所以全曲最开头那一拍在起音序列里是隐形的。

**解法**：生成拍点后判断——若网格首拍明显晚于 0，且开头确实有能量，就补一个第 0 拍。

```js
const headE = Math.max(full[1] || 0, full[2] || 0, full[3] || 0, full[4] || 0);
if (beats[0] > (period / ENV_RATE) * 0.35 && headE > medianEnergy * 0.5) beats.unshift(0);
```

## 第三个坑：八度错误（octave error）

自相关很容易把周期识别成 2 倍或 1/2 倍——即检测出 60 BPM 而不是 120，或 240 而不是 120。
听起来都对（因为 120 的每一拍都是 240 的拍），但**小节线会全错**。

**解法**：把人耳习惯的区间锁在 **80–160 BPM**，超出就把周期乘/除 2。也支持 `--bpm` 手动指定。

> [!danger] 这段修正代码曾经写反方向，导致死循环
> 正确的方向是：**周期减半 → BPM 加倍**。
> 写成 `while (bpm < 80) period *= 2` 的话，周期越大 BPM 越小，永远出不来。
> 详见 [[16 一个会挂死的bug - 数值异常绝不该变成死循环]]。

## 精度怎么验收

用 `tools/compare-beats.mjs` 对比两份打点表：

```bash
node tools/compare-beats.mjs input/song.beats.json input/song.markers.json
```

它会报平均/中位/最大偏差、**系统偏移**（带符号的中位数）、以及容差分布直方图。

> [!tip] 判读要点
> - **中位偏差 < 半帧**（24fps 下 21 毫秒）→ 合格
> - **系统偏移明显**（比如总是 +30ms）→ 其中一份有整体相位差，必须统一，不能靠"平均一下"
> - 最大偏差大但中位小 → 可能只是漏了某几拍或多了几拍
