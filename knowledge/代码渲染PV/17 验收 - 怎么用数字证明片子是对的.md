# 17 验收 - 怎么用数字证明片子是对的

> **渲染成功 ≠ 画面正确。**
> 时间轴错了、音频挪了、某段没渲染，渲染器都会开开心心地告诉你"完成"。

[[13 出片流水线 - 一条命令跑完]] 里的 `check` 已经挡掉了一类问题。这一篇讲另外两类，
以及一个很值得学的测量技巧。

## 三类验收

| 时机 | 工具 | 拦什么 |
|---|---|---|
| **渲染前** | `build.mjs check` | 数据自相矛盾（时长不符、分镜有空洞、镜头名打错……） |
| **渲染后** | `build.mjs verify` | 音频被管线挪动（音画不同步）、音轨被截断 |
| **渲染后** | `build.mjs sheet` | 视觉事故（黑屏、元素被裁、段落没生效）——用抽帧速览 |

## 音画同步验收：关键在「比两次检测的差」

**天真的做法**：把成片音轨的拍点，和打点表直接比。

**为什么不行**：节拍检测器本身在密集混音上就有约 **10 毫秒**的系统性偏差（见 [[12 自动节拍检测 - 以及一个必知的坑]]）。
直接比的话，这 10 毫秒会被算到渲染头上，得出"音画不同步"的错误结论。

**正确的做法**：做一次**对照实验**，把检测器的偏差抵消掉。

```
偏移_A = 检测(源音频)   − 打点表      ← 检测器的固有偏差
偏移_B = 检测(成片音轨) − 打点表      ← 检测器偏差 + 渲染引入的偏移
────────────────────────────────────
B − A  = 渲染管线引入的偏移            ← 这才是要验收的量
```

实测结果：

| | 中位绝对偏差 | 系统偏移 |
|---|---|---|
| 源音频 vs 打点表 | 10.7 ms | +10.3 ms |
| 成片音轨 vs 打点表 | 10.9 ms | +10.5 ms |
| **差值（渲染引入）** | — | **+0.20 ms** |

> [!tip] 这是一个通用的测量思路
> **当你怀疑某个环节有问题、但测量工具本身也有误差时，
> 就测「经过这个环节」和「不经过这个环节」的差。**
> 工具的误差在两次测量里是共模的，相减就抵消了。
>
> 温度补偿、校准曲线、A/B 测试，本质都是这一招。

**0.2 毫秒是什么概念**：24fps 下一帧是 41.7 毫秒。0.2 毫秒是**两百分之一帧**，
远在任何显示器或人眼的可辨范围之外。

## 为什么"渲染成功"不等于"对了"

本项目实际遇到过的、渲染器**不会报错**的问题：

| 问题 | 谁会报错 | 靠什么发现 |
|---|---|---|
| 分镜到 210 秒结束，但歌有 211.5 秒 | 没人 | `check` 报「结尾会黑屏」 |
| 生成器没把收尾尾巴算进时长 | 没人 | `check` 报「音频与打点表时长不符」 |
| 台词排到了镜头还没出现的时间上 | 没人 | 人工核对生成的 JSON |
| `camera` 缩放开太大，切掉界面文字 | 没人 | **出静帧看边缘** |
| 转场用交叉溶解，文字压文字 | 没人 | 出静帧看转场那一秒 |

**共同点：全都是"渲染没报错，但成片是错的"。**

## 视觉验收：不要只看你自己设计的那个时刻

`build.mjs sheet` 会抽 30~40 帧铺成一张 HTML 表，每帧标注时间码、段落名、当前镜头。

```
node tools/build.mjs sheet
# → out/sheet.html，用浏览器打开
```

**为什么必须"均匀抽样"而不是"挑几个关键时刻看"**：
你会不自觉地只看自己精心设计的那几秒，而事故往往发生在**你没在看的地方**——
段落交界、转场那一秒、画面边缘、时长末尾。

> [!warning] 小尺寸预览会骗你
> `camera` 缩放裁掉界面文字这个问题，在浏览器预览里完全看不出来，
> 因为它只在画面边缘切掉几十像素。**必须出全尺寸静帧核对边缘。**

## 参考工程怎么验收的

它做得更重：**几千张窗口截图 + 全片母版逐像素数值比对**，
差异筛选条件是"差值超过 8 级的像素占比超过 0.2%"，再人工抽看 8 个时刻。

而且它诚实标注了**验收范围**——"这不表示每个像素差值都在 8 级以内，
也不等于逐帧视觉或音画验收"。

> [!important] 验收报告要写清楚"验了什么、没验什么"
> "通过"这两个字如果不带范围，就是误导。
