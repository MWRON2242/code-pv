# 13 出片流水线 - 一条命令跑完

`tools/build.mjs` 把整条链路串起来，对应参考工程的 `build.py`。

## 命令

```bash
# 内容：文本 → JSON（不手写 JSON，见下节）
node tools/fit-script.mjs timeline
node tools/fit-script.mjs script --every 1
node tools/fit-script.mjs lyrics --every 1

# 出片
node tools/build.mjs check        # 自检：数据文件之间是否自洽
node tools/build.mjs beats <音频>  # 自动节拍检测 → input/<歌名>.beats.json
node tools/build.mjs delivery     # 交付版 → out/film.mp4（h264 720p）
node tools/build.mjs master       # 无损母版 → out/film-master.mov（ProRes 4444）
node tools/build.mjs master-lite  # 轻量母版 → out/film-master-lite.mp4（h264 CRF 1）
node tools/build.mjs 4k           # 从交付版放大 → out/film_4k.mp4
node tools/build.mjs all          # check → delivery → master
```

**分步的价值**：调画面时只跑 `delivery`（几十秒）；定稿后才跑 `master`（PNG 帧，慢一倍）。

## 文本驱动：为什么不该让人手写 JSON

JSON 是给程序读的，不是给人写的：
- 每加一句台词都要**自己算时间**，还得和节拍对齐
- 多一个逗号就解析失败，报错还很难懂
- 改一句就要手动调后面所有行的时间

所以内容全部走纯文本，由 `tools/fit-script.mjs` 排到节拍网格上：

```
# input/script.txt
you 你好
her@18.5 这句我钉死在 18.5 秒
her 你好。我在。
```

```bash
node tools/fit-script.mjs script --every 1
```

**两个设计要点：**

1. **默认区间取自分镜里对应的镜头**：台词排进 `chat` 段、歌词排进 `player` 段。
   否则会排到镜头还没出现的时间上——那些行**永远不会被看到**，而且不报错。
2. **`@时间` 钉死的行不消耗锚点**：偶尔想手动微调某一行时，不会把后面全部错位。

锚点不够时会明确告警（`有 N 行没排进去，把 --every 调小`），而不是静默丢弃。

## 自检在查什么

`check` 会在渲染前把数据之间的**矛盾**找出来——这类错误不查就会变成"渲染成功但画面不对"：

| 检查项 | 为什么 |
|---|---|
| 音频在 `public/` 里 | Remotion 的 `staticFile()` 只认 `public/`，放 `input/` 会静默无声 |
| 音频实际时长 vs 打点表时长 | 换了歌没更新打点表 → 后半段全错位 |
| 分镜的 `from` < `to` | 写反了会渲染出黑屏 |
| 分镜是否覆盖全曲 | 有空洞 → 中间黑屏；没覆盖到结尾 → 结尾黑屏 |
| 镜头名是否在注册表里 | 打错字 → 那段什么都不渲染 |
| 台词/歌词时间是否超出歌曲时长 | 超出的永远不会出现 |

## 交付版与三种母版

| | 交付版 | 无损母版 | 轻量母版 |
|---|---|---|---|
| 编码 | h264 + AAC | **ProRes 4444**（ap4h）+ PCM | h264 CRF 1 + AAC |
| 色度 | yuv420p | **yuv422p12le** | yuv420p |
| 中间帧 | JPEG | **PNG（无损）** | JPEG |
| 体积（25 秒 / 4 分钟） | 13.5 MB / 130 MB | 252 MB / **2.4 GB** | ≈15 MB / 140 MB |
| 用途 | 发布 | 底片，二次处理从它出 | 日常归档、快速二次剪辑 |

> [!warning] 无损母版会吃掉磁盘
> ProRes 4444 约 80 Mbps。**一首 4 分钟的歌约 2.4 GB。**
> 出片前先看可用空间；吃紧就改用 `master-lite`。

**母版为什么要单独出**：交付版是有损压缩，再拿它放大或二次调色，损失会累积。
母版是"底片"，任何后续处理都从它出发。

**4K 的做法**：从交付版 lanczos 放大三倍（1280×720 → 3840×2160），并不增加真实细节。
真要 4K 原生，得把 Composition 的 `width`/`height` 改成 3840×2160 重渲——那才是真细节，
但渲染时间约 9 倍。

## 一个自找的坑：命令必须在项目根目录下跑

> [!warning] 报错和参数无关时，先看工作目录
> Remotion 要靠**当前工作目录**去找入口点 `src/index.ts`。
> 在别的目录下跑会得到 `No entry point specified`——别去怀疑参数。
> `build.mjs` 内部已经把子进程的 `cwd` 固定到项目根目录，所以用它就不会踩到。

## 另一个坑：输出文件被占用，渲染白跑

**现象**：渲染跑了五六分钟，进度 100%，最后却失败：

```
Error: EPERM: operation not permitted,
  rename 'out/pv.mp4.xxxx.remotion-in-progress' -> 'out/pv.mp4'
```

**原因**：Remotion 渲染完会把临时文件**重命名**成目标文件名。
如果目标正被别的进程打开（在播放器里放着、被编辑器或 GUI 预览持有句柄），
这个 rename 需要的 DELETE 权限拿不到，就 EPERM。**错在最后一步，前面全白费。**

**判断方式有个陷阱**：不能靠「能不能打开」来判断是否被锁。
Node 在 Windows 上打开文件时会带上 `FILE_SHARE_DELETE`，
即使别的进程正占用也能打开成功——但 rename 照样失败。
唯一可靠的判断是**自己试着重命名一次**：

```js
const probe = preferred + '.lockprobe';
try {
  fs.renameSync(preferred, probe);   // 能重命名 → 没被锁
  fs.renameSync(probe, preferred);
  return preferred;
} catch {
  // 换一个带序号的名字，并明确告诉用户写到了哪里
}
```

> [!tip] 顺带一条命名经验
> 如果某个文件会被播放器/GUI **长期打开**，就不要让它当渲染目标。
> 本项目的交付版因此叫 `pv.mp4` 而不是 `film.mp4` ——
> 后者一旦被预览过就会一直被占用，每次渲染都要改名。
